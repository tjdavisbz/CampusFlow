# Chapel portal migration discovery

Status (2026-10-27): the chapel foundation schema migration has been applied to the separate `campusflow_nonprod` PostgreSQL database. The supplied Fall 2026 attendance snapshot (53,000 rows, 53 events, 1,000 students) was imported for the Nelson tenant there and a second run verified an exact, no-change match. Azure's full server backup `backup_639287420884558658` completed at 2026-10-27 23:54:49 UTC before this migration/import; the server reports 14-day backup retention and geo-redundant backup. No separate `pg_dump` was created. The student and staff attendance pages were deployed to non-production; the student page was restyled to match the current portal. Production has not been migrated, imported, or deployed for Chapel. CBORD/SFTP import is not enabled. The staff edit workflow still needs an authenticated end-to-end test.

## Confirmed legacy behavior

- The student page `eStudent/ChapelAttendance.asp` reads `SAGU_ChapelAttendancePortalSummary` and displays each chapel date, status, comment, and present/absent/excused totals. The current procedure hides future dates, but its term filters are commented out; its totals and rows can therefore span terms. The new page should filter both rows and totals to the selected term rather than reproduce that likely defect.
- `eStudent/SAGU_ChapelExcuse.asp` displays submitted excuse requests and offers a short-term request form (one to three days, work/medical/other). Its post page calls `SAGU_StudentPortal_PostChapelExcuse`. The stored-procedure definitions for the excuse read/write endpoints are not in the current checkout.
- A separate chapel-release application is present in the legacy student portal; whether to carry it forward needs confirmation from the staff portal workflow.
- `John Old SQL/Chapel SSIS/SAGU SSIS/SAGU_Odyssey_ChapelScans.dtsx` reads Odyssey scans into CAMS SQL Server and runs a sequence of chapel procedures. The later procedure definitions supplied on 2026-10-27 clarify the current rules and supersede the older checked-in SQL where they differ.
- The current `SAGU_Chapel_ImportOdysseyScans` reads `D:\SAGU SSIS Projects\Chapel\Import\ChapelAttendanceDaily.csv` with `OPENROWSET` and inserts distinct rows into `SAGU_Odyssey_ChapelScans`. The supplied WinSCP job downloads `*.csv` from `sftp.aws.cbord.com:/nelson.odyssey.cbord.com/Chapel` to that Windows import folder, then runs `rm *.csv` remotely. It uses a pinned Ed25519 host key. A separate historical PowerShell export writes `C:\ChapelOutput\data.csv` on a Windows server; that is a different path and should not be assumed to be the input for the current procedure.
- The current `SAGU_ChapelPresentStudents` joins `ID_Number` directly to `Student.StudentID` (the old SSN-derived join is commented out). For each chapel event, an early scan is from 20 minutes before through 5 minutes after start; a late scan is from 6 minutes after start through end; a checkout-window scan is from 30 minutes before end through one hour after end. Early scan plus checkout-window scan becomes Present; late scan plus checkout-window scan becomes Absent with `Late`; early scan without checkout-window scan becomes Absent with `Scan In Only`. The checkout flag predicates are commented out after the cloud Odyssey upgrade: timing, not the flag, drives classification. The new importer must validate this behavior against representative source data before activation.
- `SAGU_ChapelAbsentStudents` later marks remaining past, unclassified scheduled attendance rows Absent. `SAGU_ChapelExcusedStudents` applies weekday `ChapelExcuses` flags to past rows that are not Present. `SAGU_Chapel_BonusBank` consumes a bonus count to excuse an absence; `SAGU_Chapel_BonusChapelProcedure` can excuse an absence based on attendance at a particular chapel. These are actual application-data writes, not temp-table-only routines.
- `SAGU_Chapel_PopulateChapelAttendance` creates the expected student/event rows from chapel schedule plus housing, numeric-section enrollment, or varsity activity, excluding the manual exclusion list. It also marks eligible dorm devotional rows Present and updates recurring weekday excuses for non-residential students based on early class schedules. This requires Elements housing, enrollment, attendance type, schedule, and activity mappings; scan import alone cannot recreate the attendance population.
- `SAGU_Chapel_PopulateGroups` rebuilds the wide group table from housing assignments, commuter status, athletic activity, and an on-premises `Group Rosters.xls`. The new normalized membership table must support both derived and staff-maintained groups. The old procedure also inserts a sample account and contains one-off student-ID overrides; do not carry these hard-coded rows into the new system.
- The current `SAGU_Chapel_rptChapelAttendanceByGroup` and `SAGU_Chapel_rptChapelStatus` are reporting queries, not required to process a scan. Their temp-table updates are intermediate calculations. The group report assembles a column name into dynamic SQL and must not be reused verbatim.
- `SAGU_Chapel_EnrolledStudentsWithRoom` is a room lookup/report. `SAGU_ChapelExludedStudents` has only commented-out statements and does nothing. `SAGU_ChapelNoScanOut` is a staff exception-review/correction routine. The login table/procedure are not needed in CampusFlow.
- The staff deployment is in `ChappelAttendance/` (the folder spells Chapel with two p's). The Razor views are available, but controller and model source was compiled into `bin/ChappelAttendance.dll`. Its user-facing screens support attendance entry by date, student, and several named groups; editing weekday excuses and comments; and editing bonus-bank counts. The remaining navigation includes SSRS reports, Excel-file links, and update routines rather than in-app screens.
- The compiled controller uses direct SQL updates against `ChapelAttendance`, `ChapelExcuses`, and `SAGU_ChapelBonusBank` and a separate `ChapelLoginInfo` check. Its SQL strings are assembled by concatenation, so the port must replace that with parameterized, authorized operations.
- The table definitions supplied on 2026-10-27 listed `Nelson_ReportingAndIntegration`: `ChapelAttendance`, `ChapelBonusBank`, `ChapelExcuses`, `ChapelGroups`, `ChapelReleaseRequests`, `ChapelSchedule`, `Chapel_ExclusionList`, and `ChapelLoginInfo`. The user subsequently confirmed the live operational tables, including the supplied Fall 2026 schedule and excuses data, are still in `CAMs_Enterprise`; `ChapelBonusBank` is in `Nelson_ReportingAndIntegration`. The compiled staff app also references `CAMs_Enterprise.dbo.SAGU_ChapelBonusBank`, so both bonus-bank objects need comparison before migration. `ChapelLoginInfo` should not be carried into CampusFlow; its existing identity and permission system should control access.
- A 92,026-row pasted scan extract has columns `ID_Number`, `Activity`, `Date_Time`, `Attendance_Checkout`, and `Terminal Name`. It covers 789 distinct IDs and only 28,682 unique exact rows, so duplicate scan rows are common. There are 4,271 student+timestamp combinations with both checkout values. This is evidence that the raw data must be deduplicated and processed against a chapel schedule; `Attendance_Checkout` alone cannot determine final attendance. The `ID_Number` values resemble student IDs, but the mapping to Elements `StudentUID` still needs validation.
- The second supplied copy of the scan extract is byte-for-byte identical to the first. It is comma-separated data with five fields on all 92,027 lines (one header plus 92,026 records), from 2026-08-26 through 2026-10-23 across 28 dates. Fields are padded with spaces and must be trimmed. `Activity` includes 89,081 `Chapel Attendance` rows and 2,945 `HCC Attendance` rows; the latter appear on four dates and two dedicated HCC terminals. The legacy import procedure brings in all activities, and the current `SAGU_ChapelPresentStudents` does not filter by activity. Thus HCC scans can earn credit when they meet the scheduled event's scan-in/out windows, but the activity label itself never awards credit. The older SSIS source query also accepted three activity IDs (2, 4, 6). A 2015 ad hoc linked-server query filters to `Chapel Attendance` and `Special Chapel Attendance`, but it is not the current import/attendance-processing path; do not infer the current behavior from that query. On the four HCC dates, no student+day in the supplied extract has both HCC and regular Chapel activity, consistent with alternate scan activity rather than duplicate labels.
- The user confirms the **SSIS job** runs Wednesday, Thursday, and Friday at 1:30 p.m. Central and runs the WinSCP script plus other processing steps. A replacement schedule should use the `America/Chicago` time zone so daylight saving transitions are handled correctly. The checked-in SSIS package is an older Odyssey-direct version; it documents the legacy procedure sequence but does not contain the supplied WinSCP step, so it should not be represented as a complete copy of the currently scheduled job.
- In that older package the precedence chain is: populate new student/event attendance rows, remove excluded students, populate excuses, populate groups, recreate/fill raw scans, prune prior-term scans, mark present/late/scan-in-only, mark remaining past rows absent, apply recurring excuses, then apply bonus-bank credits. The current job may differ, but this is the end-to-end processing order recoverable from the checked-in package.
- The `SAGU_ChapelPresentStudents` procedure does not use the `Attendance_Checkout` values; the sample's conflicting-looking same-time rows may therefore be duplicate feed artifacts, but the import still needs an idempotent raw-scan key and event matching.

## Implementation guardrails

- Use new PostgreSQL tables and an auditable, repeatable import. Store a file/run identity and raw scan identity so retrying an SFTP file does not duplicate attendance.
- Do not reproduce the legacy job's unconditional remote `rm *.csv` behavior. Download to a temporary location, validate the file, record a checksum and processing state, and retain an archival copy before marking or removing a remote file. Remote deletion should be an explicitly configured final step, after a durable successful import, not part of the download step. Preserve the pinned host-key verification and keep SFTP credentials in a secret store.
- The WinSCP command downloads **all** CSV files, while the SQL procedure reads only `ChapelAttendanceDaily.csv`; the replacement must account for every downloaded file and reject unknown filenames rather than silently delete them.
- Validate student identity, term, chapel event, and timestamp before applying a scan. Quarantine ambiguous/unmatched rows for review.
- Preserve current activity behavior: do not exclude `HCC Attendance` by name. It may satisfy the same scheduled-event scan windows as `Chapel Attendance`; an activity row outside those windows earns no attendance credit. Keep `Activity` and terminal in the import audit for investigation.
- Keep manual staff overrides distinct from imported decisions and never silently overwrite them.
- Enforce the student page against the authenticated student profile only; admin pages require a dedicated chapel permission.

## Local first slice

- `AppChapelAttendanceRecords` has term ID, Elements student UID and display ID, chapel-local timestamp, one status, comment, provenance, and optional legacy attendance ID. A unique student+term+timestamp key intentionally prevents duplicate attendance decisions; source duplicates must be reviewed/deduplicated before migration.
- Staff can search by date, student, and/or imported group membership, then save a status and comment with optimistic concurrency. The page requires the dedicated `Manage chapel attendance` permission.
- A signed-in student can see only their own attendance for a selected term, with present/absent/excused counts. Future chapel dates are hidden.
- The normalized `AppChapelGroupMemberships` table is term-scoped for importing the old wide `ChapelGroups` flags, but no membership data has been copied and there is no membership editor yet.
- A strict, streaming CSV reader now parses the supplied five-column CBORD layout, trims padded fields, retains campus-local timestamps, and rejects unexpected headers or malformed rows. It has focused tests. It does not yet fetch from SFTP, store scans, classify attendance, or alter any attendance record.
- A read-only scan matcher now accepts a scheduled chapel start/end and a student's parsed scans, applies the legacy early/late/exit timing windows, and includes HCC activity. It requires distinct, chronological scan-in and scan-out timestamps; the legacy procedure could accidentally satisfy overlapping windows with one timestamp, so this case is flagged Ambiguous rather than automatically marked present/late. It has focused tests but is not connected to an attendance-writing pipeline.
